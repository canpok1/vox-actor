# Issue/PR/コメント作成ルール

## ラベルの自動付与について

- Issue作成時に `ready` ラベルを付与しないこと
- `ready` ラベルはユーザーがIssue内容を確認した後に手動で付与する運用とする
- `/create-issue` やIssue一括作成時も同様に、`ready` ラベルなしで作成すること

## 本文投稿時のエスケープ事故防止

`gh issue create` / `gh issue edit` / `gh issue comment` / `gh pr create` 等で本文を投稿する際は、以下のルールに従うこと。

### A. 本文投稿は `--body-file` を優先する

コードブロック・引用符・`$`・バックスラッシュ・`EOF` 等の終了トークン候補語を含む本文を投稿する場合、原則として **一時ファイルに書き出してから `--body-file <path>` で投稿する** こと。

理由:

- ファイル経由ならシェルのクォート/エスケープ/heredoc parse の介在を完全に避けられる
- ファイルは Read で目視確認できるため、投稿前に内容をレビューできる
- 内側に `EOF` のような終了トークン候補が含まれていても影響を受けない

### B. heredoc を使う場合のクォート種類とネスト禁止

やむを得ず `--body "$(cat <<EOF ... EOF)"` 形式を使う場合は、以下を遵守すること。

- **シングルクォート heredoc (`<<'EOF'`) を使う**: シェル展開されないため `$` ・ダブルクォート・バックティックのエスケープは不要。本文を素のまま書ける
- **クォートなし heredoc (`<<EOF`) は避ける**: `$` やバックティックがシェル展開されてしまうため、本文を素のまま書けない
- **本文中に `EOF` という単語を含めない**: 行頭の `EOF` は heredoc を終了させる。本文がコードブロック例などで `EOF` を含むなら、外側終了記号を `OUTER_EOF` 等にリネームするか、A. の方針に切り替える

### C. 投稿後の目視確認を必須化する

`gh issue create` / `gh issue edit` / `gh issue comment` / `gh pr create` を実行した直後に、必ず以下のいずれかで本文の表示を確認すること。

- `gh issue view <num>` / `gh pr view <num>`
- `gh issue list` で件数のみ確認するのは不十分（本文の表示崩れに気付けない）

確認の結果、表示崩れがあれば即座に修正する。
