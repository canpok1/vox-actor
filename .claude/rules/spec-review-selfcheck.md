# 仕様書レビュー時のセルフチェックルール

仕様書（`docs/` 配下）を作成・更新した際は、PRを出す前に以下のセルフチェックを実施すること。

## 1. 用語・引数名の一貫性チェック

- 同一の概念には同一の用語を使っているか（例: 「パス」と「ディレクトリ」の混在に注意）
- コマンド引数名が全セクションで統一されているか（例: `<path>` と `watch_directory` の混在がないか）
- 複数モードがある場合、各モードの説明で同じパラメータ名・オプション名を使っているか
- 用語の表記揺れがないか（例: 「読み上げ」と「再生」、「台本」と「スクリプト」）

## 2. セクション間の整合性チェック

- 概要セクションの記述が、詳細セクションの内容と矛盾していないか
- 概要文が特定モードに限定された表現になっていないか（全モードを包含する記述か）
- コマンド構成セクションのオプション一覧と、他セクションで参照されるオプションが一致しているか
- 実行フローと、エラーハンドリングセクションの記述に矛盾がないか
- 終了コードの定義と、エラーハンドリングの挙動が整合しているか

## 3. エラーハンドリングの具体性チェック

以下の項目が明記されているか確認する:

- **リトライ**: リトライの有無。リトライする場合は回数・間隔・対象条件を記載しているか
- **タイムアウト**: タイムアウトの有無と、ある場合はその秒数
- **エラー時の動作**: スキップして続行するのか、即座に終了するのか
- **出力**: エラーメッセージの出力先（stderr等）が明確か

## 4. レビュー指摘の集約対応ルール

- レビュー（CodeRabbit等）から指摘を受けた場合、**全ての指摘を確認してから**まとめて対応すること
- 指摘1件ごとに即座にコミットせず、関連する指摘をグルーピングして1コミットにまとめる
- これにより、短時間のコミット集中によるレート制限を回避する
